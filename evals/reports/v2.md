2026-11-02。v1 と同じ brief・期待値・予算で、新しい writer-b と reader-b を実行した。過去の候補、レポート、期待値、実装は閲覧禁止。

点数は改善していない。v1 から満点の小さい課題なので、一般的な書きやすさを定量的に改善したとは主張しない。変更の効果は具体的な曖昧さへの反応で判断する。

writer-b:

> 「`id` は必須の固定名ではありません。`input.noteId` 等も使えます。」

> 「`check` は policy/operation 名の構文と境界を検査し、host の実登録は調べません。」

この二つを候補の判断根拠に挙げ、source 記述で混乱した箇所はないと回答した。一方、host adapter の登録手順は残る課題とした。

reader-b:

> 「名前だけから所有者判定等を推測しない」

> 「adapter 本体の副作用を完全に証明するものではない」

過大な security/performance 推論を抑制する文言として有効だと回答した。resume の初期化省略や context の提供元は引き続き言語仕様への依存であり、ソース単体だけの読解成功とは呼ばない。

根拠は [writer-b log](../attempts/writer-b/log.md)、[reader-b log](../attempts/reader-b/log.md)、各 results.json。`just eval` は corpus と保存した4参加者の候補・回答を再採点する。新しい LLM 参加者を自動実行するコマンドではない。

この時点では同じ小課題の再反復より、次の評価を「host adapter を登録して動かす」「拒否された RPC の error を UI へ出す」「import で複数ファイルへ分ける」に広げる価値が高い。後二つの言語機能はまだ未実装であり、現在の成功点数へ含めない。
